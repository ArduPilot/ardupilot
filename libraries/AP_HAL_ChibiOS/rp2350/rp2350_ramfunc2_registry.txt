# RP2350 RAMFUNC2 registry
# format: path|symbol
#
# An entry that matches no symbol fails the copter firmware build with "no
# symbol match". A silent miss is a trap - the build succeeds and the entry
# looks like it took effect. Other vehicles and the bootloader skip the check,
# as most entries are legitimately absent there.
#
# An entry whose symbol only exists under some build option carries a
# "[needs <DEFINE>]" marker. The generator reads that define out of the
# generated hwdef.h and stays quiet when it is off, while still failing if the
# define is on and the symbol is missing - which would be a real miss. The
# __stats_* entries below are the case in point: they need
# HAL_ENABLE_THREAD_STATISTICS, which is off in every flight build.
#
# An option that defaults on outside hwdef.h takes "[unless <DEFINE>]" instead,
# which stays quiet only when hwdef.h explicitly sets the define to 0 or FALSE.
# A symbol that only exists while an option is off takes "[without <DEFINE>]",
# which stays quiet when hwdef.h turns the define on.
#
# A header-defined function only gets an out-of-line copy once enough callers
# exist, and a board that compiles a reduced set of them can inline it away
# completely. No define expresses that, so those entries carry "[inlinable]"
# and are the one kind of miss the check forgives. Use it only where the symbol
# really does come from a .h - a typo in a .cpp entry must still be fatal.
#
# An entry for some vehicles lists their programs, as "[arduplane]" or
# "[arducopter,arduplane]": it is placed, and a miss of it fails the build, only
# when waf links one of them for hardware, and other programs ignore it. Its picks
# name those programs' own objects and lib<vehicle>_libs.a, so it can name code
# other vehicles share without moving theirs, even when one waf run links several
# programs; code from shared archives (ChibiOS, libc, libm) cannot be limited this
# way. It combines with "[inlinable]". A name that is not a vehicle program fails
# every build, so a misspelt marker is not taken for one.

# Boot-order hazard for the libc helpers. The compiler lowers struct/array init
# in early boot into implicit calls to memcpy/memset and the 64-bit divide
# helpers, and those run before rp_clock_init() copies .ramtext to SRAM
# (rp_clocks.c). Relocating a helper that early boot calls executes
# uninitialised SRAM and the FC double-faults.
#
# memcpy and memset ARE in SRAM, but not from here - they come from
# rp2350/rp2350_memfunctions.S, which replaces the C library's versions and
# places them in its own .ramtext section. It is safe because the copy loop in
# rp_clocks.c was rewritten as a volatile word loop so it no longer calls
# them. See the memcpy/memset section of rp2350/DEVELOPMENT.md before
# touching that, and do not add entries for them here.
#
# __udivmoddi4 and __aeabi_uldivmod are NOT relocated and must stay in flash -
# nothing has been done to keep them off the early-boot path. They profile hot
# on core1 (~4.4% of active time); claw that back by removing the calls (e.g.
# 32-bit micros() deltas) rather than by moving the symbol. They also live in
# libgcc, which has no per-function sections, so a symbol entry silently
# matches nothing - an (archive) entry would be needed, and would boot-fault.

# newlib single-precision trig, from a core0 PC-sampler run on RPI_UAVFC.
# The AHRS/EKF math on core0 keeps these in the XIP working set: atan2f 0.4%,
# kernel_cosf/kernel_sinf/sinf 0.2% each, atanf 0.1% of all core0 samples,
# ~1.3% together and all flash-resident. cosf is included for symmetry with
# sinf rather than on its own sample count.
# Unlike memcpy/memset these are not reachable from early boot, so there is no
# .ramtext copy-order hazard.

# reached when a filter cutoff actually changes.
