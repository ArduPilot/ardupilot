# Working process for the Zephyr port

The no-west decision and its reasoning are in
[ARCHITECTURAL.md](ARCHITECTURAL.md). Building is in [README.md](README.md).
This is the procedure and the standing choices.

## Local changes to Zephyr

If Zephyr itself needs a change that is not upstream yet:

* Carry it as commits on a local branch of the `modules/zephyr` submodule, and
  pin the parent's gitlink to that branch tip. The submodule is the single
  copy: a parallel `.patch` tree here was never applied or checked by anything
  in the build, so it could go stale without anyone noticing.
* Use Zephyr's contribution trailers on anything upstream-bound:
  `Signed-off-by:` for the DCO, and `Assisted-by: <Agent>:<model> <tools>` for
  AI-assisted work.
* Upstream it when practical, then move the pinned revision back to an upstream
  commit.

**Do not check out the archival `main` / IT-BUILDS branch in the live
`modules/zephyr` working tree.** It sits on a much older Zephyr base, thousands
of source files differ from the working `~v4.4.0-7936` branches, and it tracks
the dependency directories as gitlinks. Switching to it churns the whole tree
and deletes the TSV-generated dependency checkouts. Inspect it in a throwaway
`git worktree`.

Never operate on `modules/zephyr` from two places at once. A human checkout
racing a script's reset, clean or clone corrupts the working tree.

## Dependency pinning

Guardrails:

* Do not run west in the ArduPilot repository root.
* Do not keep a west workspace rooted at `ardupilot/` or `ardupilot/modules/`.
* Do not commit west-generated workspace state outside `modules/zephyr`.
* Root-level ArduPilot submodules, `modules/zephyr` included, are the usual
  `.gitmodules` plus parent gitlink.
* Source of truth for the *nested* Zephyr dependency set is
  `zephyr_manifest_v4_4_0_map.tsv`, not `.gitmodules`. The autogenerated
  `.gitmodules` block was removed; that file lists only real, git-enforceable
  submodules.

`sync_generated_zephyr_submodules()` in
`Tools/zephyr/zephyr_get_prerequisites.sh` materialises every dependency from
the TSV as an untracked embedded checkout at its pinned SHA, and adds their
top-level paths to the submodule's `.git/info/exclude` so `git status` stays
quiet. Delete any dependency directory and a re-run regenerates it byte for
byte.

Change a dependency version by editing the TSV and re-running the sync, never
by updating a checkout in place.

TSV caveats:

* Authoritative but **not enforced**. Nothing fails if a dependency on disk
  drifts from its TSV SHA, and three HALs have drifted silently. A drift check
  in the script or in CI is the mitigation, and does not exist yet.
* The filename says `v4_4_0`. The pinned Zephyr base is a main-branch snapshot
  about 7,900 commits past the v4.4.0 tag. Re-pinning to a release or LTS is a
  separate decision.
* Re-cloning the roughly 84 repositories is a 7 GB network fetch with no local
  object reuse. A shared git object cache (`--reference` or alternates) in the
  sync would make wipe-and-regenerate cheap.

## Resolving new pins with west, outside this repo

West runs once, as a metadata resolver, to discover the commit SHAs for a
Zephyr manifest revision. Its output is translated into the TSV and committed.

```sh
mkdir -p /tmp/zephyr-bootstrap && cd /tmp/zephyr-bootstrap
west init -m https://github.com/zephyrproject-rtos/zephyr --mr <zephyr-tag-or-sha> ws
cd ws && west update
west manifest --freeze > frozen-west.yml    # exact resolved SHAs
```

Translate the resolved projects into rows of
`zephyr_manifest_v4_4_0_map.tsv`, tab separated: name, URL, SHA, path. The TSV
is board-agnostic, so capture the whole manifest, not a per-board subset. Then
delete the workspace.

A resolved project with name `hal_nxp`, URL
`https://github.com/zephyrproject-rtos/hal_nxp`, path `modules/hal/nxp` and
revision `<sha>` becomes one row, and that row is the entire pinning action:
`<TAB>` below is one literal tab character.

```text
hal_nxp<TAB>https://github.com/zephyrproject-rtos/hal_nxp<TAB><sha><TAB>modules/hal/nxp
```

`./Tools/zephyr/zephyr_get_prerequisites.sh` then clones and checks out
`modules/zephyr/modules/hal/nxp` at that SHA. Do not try
`git submodule add modules/zephyr/modules/hal/nxp`: git rejects paths inside
the `modules/zephyr` gitlink, which is why the TSV exists.

The TSV captures the entire manifest, so there is no minimum set to curate.
Every dependency any board needs is already pinned.

## When to revisit no-west

* Zephyr module churn gets too painful to maintain with plain submodules.
* Upstream integration needs west-specific manifest behaviour that is awkward
  to reproduce locally.
* Maintaining the Zephyr dependency set inside ArduPilot becomes materially
  more complex than using west directly.

The third is arguably already met. The nested dependencies cannot be real
submodules because of the gitlink boundary, so they live as a TSV plus a
generator plus `.git/info/exclude`. That is more moving parts than either plain
submodules or west.

Two clean end-states, neither adopted:

1. **Fork branch.** One commit on the `modules/zephyr` fork carries the
   dependency gitlinks; the parent pins it. Pure
   `git submodule update --recursive`, fully git-enforced. Costs a rebase of
   that commit on every Zephyr bump, and the pin always points at the fork.
2. **Sibling layout**, the better of the two if we act. Dependencies move to
   `modules/zephyr_deps/...` as ordinary top-level parent submodules, no fork
   and no TSV, with `ZEPHYR_MODULES=<list>` passed to the CMake build. This is
   the layout Zephyr expects, modules beside zephyr rather than inside it; the
   current in-tree placement is the anomaly.

Working assumption until one is chosen: TSV-pinned nested dependencies
regenerated by the prerequisites script, a real git submodule for
`modules/zephyr` itself, CMake for Zephyr build logic, waf for top-level
orchestration.

## All four boards are current targets

`mr_vmu_rt1176`, `CubeOrangeZephyr`, `ESP32S3Zephyr` and `native_sim` are all
maintained. They are the four board directories under
`libraries/AP_HAL_Zephyr/hwdef/`, which also holds the shared `common/`.
Calling rt1176 the primary board is a prioritisation statement, not an
exclusion. A breakage on any of the four is an
error to fix. Only `CubeOrangeZephyr` and `mr_vmu_rt1176` are exercised by CI;
see Regression testing below.

Shared HAL work is proven first on the ChibiOS-comparable targets that already
boot, CubeOrangeZephyr primarily and then ESP32S3Zephyr, because those give a
known-good baseline to diff against. rt1176 is validated once the HAL is
trusted. Per-board verification state is in
[COMPARED_TO_CHIBIOS.md](COMPARED_TO_CHIBIOS.md).

## Logging is on by default

`CONFIG_LOG=y` is the default for every board. Disable it board-by-board only,
on boards known working that no longer need it. Extra boot and early-console
verbosity is an acceptable price.

With `CONFIG_LOG=n`, every `LOG_ERR` and `LOG_WRN` in the drivers compiles out,
and so do Zephyr's fatal-error dumps, so crashes become silent resets.

The base `zephyr/prj.conf` carries `CONFIG_LOG=y` and `CONFIG_CONSOLE=y`.
`LOG=y` alone is not enough: it needs a sink, and `LOG_BACKEND_UART` depends on
`UART_CONSOLE`, which is per-SoC and needs the devicetree `zephyr,console`
chosen node. A known-working board may set `CONFIG_LOG=n` in its own fragment
with a comment citing this; `prj.nxprt1176.conf` is the pattern, and has a
cbprintf bug as extra justification. Never disable it preemptively on a board
still in bring-up.

## Console and MAVLink on USB CDC

USB CDC is enabled on every target that has USB, the console goes over USB CDC
by default, and early kernel boot messages go there too. One cable, one
workflow, and console plus log output visible without a debug probe or extra
UART wiring.

Point the devicetree `chosen { zephyr,console }` at a CDC ACM instance, or at
the SoC's own USB serial, so the boot banner and early init prints land on USB.
Output emitted before USB enumerates is subject to the driver's buffering; that
loss window is accepted. Enable the USB device stack in the board fragment.
`zephyr,shell-uart` follows the console.

**MAVLink on USB CDC as SERIAL0 is required from boot, by design.** Do not
propose moving MAVLink off USB CDC, moving it to a UART to avoid contention,
making it opt-in, or reordering `SERIAL_ORDER` so USB is not SERIAL0. A console
CDC must not displace it: share the endpoint, or add a second CDC instance
as a composite device. Fix contention on its own terms.

| Board              | Console state                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `ESP32S3Zephyr`    | Done. Dual-USB-port board, see below: console on UART/PROG USB; MAVLink + JTAG on native USB. |
| `mr_vmu_rt1176`    | MAVLink SERIAL0 on OTG1 CDC. Console needs a CDC instance, most likely a dual-CDC composite. |
| `CubeOrangeZephyr` | Console needs moving onto USB CDC.                                                           |
| `native_sim`       | No USB. Console stays on stdout.                                                             |

A move counts as done when the console has been seen over the USB port on
hardware.

## ESP32-S3 is a dual-USB-port board

`ESP32S3Zephyr` meets the purpose of the rule above: the console is always on
a USB cable. It reaches that through the board's second USB port, not through
CDC, because CDC would cost the debugger. The S3 has a
single USB PHY on GPIO19/20, shared by the built-in USB-Serial/JTAG controller
(`303a:1001`) and the USB OTG controller. Starting the OTG device stack takes
the PHY and the JTAG controller disappears from the bus, so one USB port cannot
carry both a CDC device and JTAG at the same time. The board is therefore run
with two USB cables:

| USB port                | Device                                   | Job                                   |
| ----------------------- | ---------------------------------------- | ------------------------------------- |
| Native USB (GPIO19/20)  | built-in USB-Serial/JTAG, `303a:1001`    | JTAG debugging with OpenOCD and GDB, plus MAVLink SERIAL0 on its CDC serial (`usb_serial`, `/dev/ttyACM*`) |
| UART / PROG             | onboard USB-UART bridge to uart0 (GPIO43/44) | console, `printk`, crash dumps, `esptool` flashing |

MAVLink is on both the native USB port (SERIAL0, `SERIAL_ORDER OTG1`, which
the generator maps to `usb_serial` when no OTG CDC node exists) and the WiFi
softAP (TCP 5760, UDP 14550). The built-in controller's CDC serial and JTAG
are one composite device in silicon, so they coexist. The app runs no USB
device stack: `&usb_otg` and `cdc_acm0` are disabled in the board devicetree
and `CONFIG_USB_DEVICE_STACK_NEXT=n` in `prj.ESP32S3Zephyr.conf`. Do not
re-enable them; that silently removes JTAG and the `usb_serial` MAVLink port.

The chosen block is:

```dts
chosen {
    zephyr,console    = &uart0;
    zephyr,shell-uart = &uart0;
};
```

## ESP32-S3 flash, console and debug

* **Console** is uart0 at 115200 on the UART/PROG port, for example
  `/dev/ttyUSB0` through the DevKitC's CP210x.
* **JTAG** uses the Espressif OpenOCD fork with Zephyr awareness and a single
  core. SMP plus `ESP_RTOS Zephyr` fails while the targets are created:

  ```sh
  ~/openocd-espressif/src/openocd -s ~/openocd-espressif/tcl \
      -c 'set ESP_RTOS Zephyr; set ESP_ONLYCPU 1' -f board/esp32s3-builtin.cfg
  xtensa-espressif_esp32s3_zephyr-elf-gdb build/ESP32S3Zephyr/zephyr_build/zephyr/zephyr.elf \
      -ex 'target extended-remote :3333'
  ```
* **`waf --upload`** calls `esptool write-flash 0x0 zephyr.bin` for any board
  whose `ZEPHYR_BOARD` contains `esp32`. Put the board in bootloader mode with
  BOOT plus RESET first, or esptool fails with "Write timeout".
* **OpenOCD** needs the Espressif fork. The distro 0.12.0 build does not
  support `303a:1001`.

## Regression testing

There is no automated build, flash, soak and compare pipeline **on hardware**,
and we are not building one. Every hardware result comes from someone at the
bench with the `Tools/zephyr/zephyr_*.py` toolkit: maintain it, extend it, fix
the scripts in place when they break. [DEBUGGING.md](DEBUGGING.md) lists what
each one does.

Emulation is automated. `.github/workflows/test_renode_zephyr.yml` runs three
jobs on manual dispatch, and on every push and pull request that touches
`ArduCopter/`, `libraries/`, `modules/`, `Tools/ardupilotwaf/`, `Tools/renode/`,
`Tools/scripts/`, `waf`, `wscript`, `.github/actions/` or the workflow file
itself:

* `cubeorange-zephyr-flight` builds the CubeOrangeZephyr bootloader, then the
  copter, then flies the copter mission under Renode.
* `rt1176-zephyr-flight` does the same for `mr_vmu_rt1176`, with a boot check
  before the flight: `Tools/renode/zephyr_boot_check.py --assert-edma` waits for
  a MAVLink HEARTBEAT on `sysbus.lpuart4` and then requires that the emulated
  eDMA moved at least one byte. The heartbeat on its own does not prove the DMA
  path: `UARTDriver::_begin` falls back to the interrupt path when the async
  callback cannot be set or a DMA buffer cannot be allocated, and the board
  boots and heartbeats either way. [DEBUGGING.md](DEBUGGING.md) has that pair
  of failures, including which of them prints nothing at all.
* `chibios-reference-flight` flies a ChibiOS CubeOrange over the same Renode
  platform, the same actuator overlay, the same mission and the same
  `Tools/renode/tests/CubeOrange-copter.parm`. Only the HAL differs, so a bad
  Zephyr landing can be put down to AP_HAL_Zephyr rather than to the emulated
  board the two share.

Four Zephyr binaries come out of it - a bootloader and a copter for each of the
two boards - uploaded as `.elf`, `.bin` and `.apj` together with the ChibiOS
reference copter, the flight `.tlog`, the Renode log and a GIF of the track.
There is no emulation build variant any more: the image CI flies is the image it
publishes is the image you flash.

CI runs a pinned prebuilt Renode, downloaded by
`Tools/renode/tests/fetch_renode.sh` into `build/renode` and checked against a
SHA-256 in the workflow. A change to a local Renode checkout can never
reach CI. Peripheral fixes have to be repo-local `.cs` models under
`Tools/renode/peripherals/`, which is what the ten NXP models and the STM32 ones
already are.

`ESP32S3Zephyr` and `native_sim` appear in no workflow at all. Nothing outside
the bench builds them.

The peripheral models have their own tests, in the other Renode workflow.
`.github/workflows/test_renode.yml` runs `pytest -q Tools/renode/tests` and then
flies a ChibiOS quadplane, and neither step tolerates a failure, so that is the
job that turns red for a broken model or a broken harness. It triggers on
`libraries/**` too, so a HAL change runs it.

### A green job means the board flew

Every flight step in `test_renode_zephyr.yml` ends in `exit $rc`, the ChibiOS
reference flight included, and so does the rt1176 boot check. A failure
becomes an `::error title=...` annotation naming the verdict, one line in the
step summary, and a red job; the run still uploads the flight log, GIF and
Renode logs as artifacts, so the evidence for a bad landing survives the
failure that reports it.

The verdict line is still the thing to read. `check_copter_result()` in
`Tools/renode/tests/test_physics_flight.py` prints the first line below when the
mission passes, and raises the others; the harness catches those and prints
`Renode physics flight failed: <verdict>` before exiting 1:

```text
Copter mission passed: <N>m high, <N>m from home, roll<=<N>, pitch<=<N>, sensors healthy
Copter sensors were not healthy: 0x<flags> required 0x<flags>
Copter did not fly the expected mission
Copter landing was inaccurate: altitude <N>m distance <N>m
Copter was unstable: roll <N> pitch <N>
```

The step summary greps for those phrases. `no flight verdict line found` in the
summary means the harness died before reaching a verdict, which is a worse
result than any of the failures above, not a better one. The boot check's
equivalent lines are `HEARTBEAT after <N>s` or `no heartbeat within <N>s`, then
`eDMA moved <N> bytes` under `--assert-edma`.

The rt1176 flight step runs even when the boot check has already failed, and
spends its full timeout finding out. The boot annotation is what says why.

### What an emulated flight does not prove

[DEBUGGING.md](DEBUGGING.md) carries one more limit of its own: the Renode
platforms model memory as plain mapped memory, with no wait states and no
caches anywhere, so a code-placement change reads as zero there.

* **Sample rates.** The Renode IMU models publish at a compiled-in period and
  decode no sample-rate register, so declared and delivered rates disagree on
  every lane, on both HALs. Under `Tools/renode/peripherals/sensors/`:
  `AP_InvensenseV2.cs` free-runs its `LimitTimer` at `SamplePeriodUs = 889`,
  `AP_ICM42688.cs` at `SamplePeriodUs = 1000`, and `AP_ICM20689.cs`
  manufactures samples per FIFO-count poll at a fixed 1000 us spacing, with an
  8000 us fallback whenever the physics timestamp has not advanced. An emulated
  flight therefore cannot validate IMU rate work, and it cannot catch a rate
  regression either: the copter path checks MAVLink only.
  `check_copter_result()` reads sensor health, altitude, distance and attitude,
  and never opens the dataflash log, because `extract_flight_log()` is called
  from the plane path alone. A `GHz` value pinned at its compiled-in nominal is
  perfectly steady, so this reads as health rather than as a fault.
* **Read-only memory.** Renode models flash as writable, so an emulated board
  runs happily with a thread stack sitting in flash. CubeOrangeZephyr did
  exactly that: its devicetree declared no DTCM, Zephyr emitted the `__dtcm_*`
  sections as PROGBITS at a flash address without complaining, and every
  device-bus thread got a stack there. On silicon the first bus thread to push a
  register wrote to read-only memory and ended up branching to zero.
  `DeviceBus.cpp` and `Scheduler.cpp` now guard those sections on
  `DT_HAS_CHOSEN(zephyr_dtcm)`, but no amount of Renode testing finds that class
  of bug.
* **Anything a model does not implement.** A missing bit reads as zero and the
  firmware waits for it. The CubeOrangeZephyr fly-away was exactly that: the
  emulated PWR model never set the supply-ready bit the STM32 USB driver spins
  on, so every emulated boot sat out the HAL's USB timeout and reached its first
  IMU sample too late for the INS rate estimate to converge. The chain is in
  [ARCHITECTURAL.md](ARCHITECTURAL.md) and the model fix in
  [Tools/renode/README.md](../../Tools/renode/README.md). The lesson is the
  shape: an emulator-only stall shows up as a sensor or navigation fault, never
  as "slow boot".

### Fly the harness's own build

Each scenario in `COPTER_PROFILES` carries its own `build` function, and that
function is where the parameter file is embedded. `build_zephyr_copter()` in
`Tools/renode/tests/test_physics_flight.py` runs:

```sh
./waf configure --board CubeOrangeZephyr \
  --default-parameters Tools/renode/tests/CubeOrange-copter.parm
./waf copter
```

`build_rt1176_copter()` is the same with `mr_vmu_rt1176-copter.parm`. Both parm
files set `FRAME_CLASS 1` and `SCHED_LOOP_RATE 125`, and 125 Hz is what the
physics feed is paced at.

So do not hand-build an ELF and then fly it with `--skip-build`. A hand
configure drops the defaults silently: `FRAME_CLASS` falls back to 0, the loop
rate to the 400 Hz copter default, and the EKF stays in constant-position mode.
That is the one way to fly firmware that is not the firmware you meant to test;
the recorded instance sat there for a ten-minute flight before anyone noticed.
