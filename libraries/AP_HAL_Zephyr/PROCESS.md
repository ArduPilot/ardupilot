# Working process for the Zephyr port

The no-west decision and its reasoning are in
[ARCHITECTURAL.md](ARCHITECTURAL.md). Building is in [README.md](README.md).
This is the procedure and the standing choices.

## Local changes to Zephyr

If Zephyr itself needs a change that is not upstream yet:

- Carry it as commits on a local branch of the `modules/zephyr` submodule, and
  pin the parent's gitlink to that branch tip. The submodule is the single
  copy: a parallel `.patch` tree here was never applied or checked by anything
  in the build, so it could go stale without anyone noticing.
- Use Zephyr's contribution trailers on anything upstream-bound:
  `Signed-off-by:` for the DCO, and `Assisted-by: <Agent>:<model> <tools>` for
  AI-assisted work.
- Upstream it when practical, then move the pinned revision back to an upstream
  commit.

**Do not check out the archival `main` / IT-BUILDS branch in the live
`modules/zephyr` working tree.** It sits on a much older Zephyr base, thousands
of source files differ from the working `~v4.4.0-7936` branches, and it tracks
the dependency directories as gitlinks. Switching to it churns the whole tree
and deletes the TSV-generated dependency checkouts. Inspect it in a throwaway
`git worktree`.

Never operate on `modules/zephyr` from two places at once. A human checkout
racing a script's reset, clean or clone corrupts the working tree.

## Dependency pinning

Guardrails:

- Do not run west in the ArduPilot repository root.
- Do not keep a west workspace rooted at `ardupilot/` or `ardupilot/modules/`.
- Do not commit west-generated workspace state outside `modules/zephyr`.
- Root-level ArduPilot submodules, `modules/zephyr` included, are the usual
  `.gitmodules` plus parent gitlink.
- Source of truth for the *nested* Zephyr dependency set is
  `zephyr_manifest_v4_4_0_map.tsv`, not `.gitmodules`. The autogenerated
  `.gitmodules` block was removed; that file lists only real, git-enforceable
  submodules.

`sync_generated_zephyr_submodules()` in
`Tools/scripts/zephyr_get_prerequisites.sh` materialises every dependency from
the TSV as an untracked embedded checkout at its pinned SHA, and adds their
top-level paths to the submodule's `.git/info/exclude` so `git status` stays
quiet. Delete any dependency directory and a re-run regenerates it byte for
byte.

Change a dependency version by editing the TSV and re-running the sync, never
by updating a checkout in place.

TSV caveats:

- Authoritative but **not enforced**. Nothing fails if a dependency on disk
  drifts from its TSV SHA, and three HALs have drifted silently. A drift check
  in the script or in CI is the mitigation, and does not exist yet.
- The filename says `v4_4_0`. The pinned Zephyr base is a main-branch snapshot
  about 7,900 commits past the v4.4.0 tag. Re-pinning to a release or LTS is a
  separate decision.
- Re-cloning the roughly 84 repositories is a 7 GB network fetch with no local
  object reuse. A shared git object cache (`--reference` or alternates) in the
  sync would make wipe-and-regenerate cheap.

## Resolving new pins with west, outside this repo

West runs once, as a metadata resolver, to discover the commit SHAs for a
Zephyr manifest revision. Its output is translated into the TSV and committed.

```sh
mkdir -p /tmp/zephyr-bootstrap && cd /tmp/zephyr-bootstrap
west init -m https://github.com/zephyrproject-rtos/zephyr --mr <zephyr-tag-or-sha> ws
cd ws && west update
west manifest --freeze > frozen-west.yml    # exact resolved SHAs
```

Translate the resolved projects into rows of
`zephyr_manifest_v4_4_0_map.tsv`, tab separated: name, URL, SHA, path. The TSV
is board-agnostic, so capture the whole manifest, not a per-board subset. Then
delete the workspace.

A resolved project with name `hal_nxp`, URL
`https://github.com/zephyrproject-rtos/hal_nxp`, path `modules/hal/nxp` and
revision `<sha>` becomes one row, and that row is the entire pinning action:
`<TAB>` below is one literal tab character.

```text
hal_nxp<TAB>https://github.com/zephyrproject-rtos/hal_nxp<TAB><sha><TAB>modules/hal/nxp
```

`./Tools/scripts/zephyr_get_prerequisites.sh` then clones and checks out
`modules/zephyr/modules/hal/nxp` at that SHA. Do not try
`git submodule add modules/zephyr/modules/hal/nxp`: git rejects paths inside
the `modules/zephyr` gitlink, which is why the TSV exists.

The TSV captures the entire manifest, so there is no minimum set to curate.
Every dependency any board needs is already pinned.

## When to revisit no-west

- Zephyr module churn gets too painful to maintain with plain submodules.
- Upstream integration needs west-specific manifest behaviour that is awkward
  to reproduce locally.
- Maintaining the Zephyr dependency set inside ArduPilot becomes materially
  more complex than using west directly.

The third is arguably already met. The nested dependencies cannot be real
submodules because of the gitlink boundary, so they live as a TSV plus a
generator plus `.git/info/exclude`. That is more moving parts than either plain
submodules or west.

Two clean end-states, neither adopted:

1. **Vendoring branch.** One commit on the `modules/zephyr` fork carries the
   dependency gitlinks; the parent pins it. Pure
   `git submodule update --recursive`, fully git-enforced. Costs a rebase of
   that commit on every Zephyr bump, and the pin always points at the fork.
2. **Sibling layout**, the better of the two if we act. Dependencies move to
   `modules/zephyr_deps/...` as ordinary top-level parent submodules, no fork
   and no TSV, with `ZEPHYR_MODULES=<list>` passed to the CMake build. This is
   the layout Zephyr expects, modules beside zephyr rather than inside it; the
   current in-tree placement is the anomaly.

Working assumption until one is chosen: TSV-pinned nested dependencies
regenerated by the prerequisites script, a real git submodule for
`modules/zephyr` itself, CMake for Zephyr build logic, waf for top-level
orchestration.

## All five boards are current targets

`mr_vmu_rt1176`, `CubeOrangeZephyr`, `ESP32S3Zephyr` and
`native_sim` are all maintained. Calling rt1176 the primary board is a
prioritisation statement, not an exclusion. A breakage on any of the five is an
error to fix.

Shared HAL work is proven first on the ChibiOS-comparable targets that already
boot, CubeOrangeZephyr primarily and then ESP32S3Zephyr, because those give a
known-good baseline to diff against. rt1176 is validated once the HAL is
trusted. Per-board verification state is in
[COMPARED_TO_CHIBIOS.md](COMPARED_TO_CHIBIOS.md).

## Logging is on by default

`CONFIG_LOG=y` is the default for every board. Disable it board-by-board only,
on boards known working that no longer need it. Extra boot and early-console
verbosity is an acceptable price.

With `CONFIG_LOG=n`, every `LOG_ERR` and `LOG_WRN` in the drivers compiles out,
and so do Zephyr's fatal-error dumps, so crashes become silent resets. A
watchdog reset at WiFi AP start on the C6 presented as an unexplained `rst:0xc`
reboot loop that logging would have named immediately.

The base `zephyr/prj.conf` carries `CONFIG_LOG=y` and `CONFIG_CONSOLE=y`.
`LOG=y` alone is not enough: it needs a sink, and `LOG_BACKEND_UART` depends on
`UART_CONSOLE`, which is per-SoC and needs the devicetree `zephyr,console`
chosen node. A known-working board may set `CONFIG_LOG=n` in its own fragment
with a comment citing this; `prj.nxprt1176.conf` is the pattern, and has a
cbprintf bug as extra justification. Never disable it preemptively on a board
still in bring-up.

## Console and MAVLink on USB CDC

USB CDC is enabled on every target that has USB, the console goes over USB CDC
by default, and early kernel boot messages go there too. One cable, one
workflow, and console plus log output visible without a debug probe or extra
UART wiring.

Point the devicetree `chosen { zephyr,console }` at a CDC ACM instance, or at
the SoC's own USB serial, so the boot banner and early init prints land on USB.
Output emitted before USB enumerates is subject to the driver's buffering; that
loss window is accepted. Enable the USB device stack in the board fragment.
`zephyr,shell-uart` follows the console.

**MAVLink on USB CDC as SERIAL0 is required from boot, by design.** Do not
propose moving MAVLink off USB CDC, moving it to a UART to avoid contention,
making it opt-in, or reordering `SERIAL_ORDER` so USB is not SERIAL0. A console
CDC must not displace it: share the endpoint the way the C6 does, or add a
second CDC instance as a composite device. Fix contention on its own terms.

| Board              | Console state                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `ESP32S3Zephyr`    | MAVLink on OTG CDC-ACM. Console placement needs checking.                                    |
| `mr_vmu_rt1176`    | MAVLink SERIAL0 on OTG1 CDC. Console needs a CDC instance, most likely a dual-CDC composite. |
| `CubeOrangeZephyr` | Console needs moving onto USB CDC.                                                           |
| `native_sim`       | No USB. Console stays on stdout.                                                             |

A move counts as done when the console has been seen over the USB port on
hardware.

On ESP32-S3 the chosen block is:

```dts
chosen {
    zephyr,console    = &cdc_acm0;
    zephyr,shell-uart = &cdc_acm0;
};
```

with `&usb_serial { status = "disabled"; };` to free the shared GPIO19/20 pins
for the OTG peripheral. One exception, for early bring-up only: point the
console at `&uart0`, which the ESP32-S3's built-in JTAG/serial bridge forwards
to `/dev/ttyACM0`, when the USB OTG stack is not yet known to work and you need
to see boot panics. Revert once the board boots reliably. Never commit a
uart0-only console devicetree.

## ESP32-S3 flash and console

- **Two USB peripherals share GPIO19/20.** `303a:1001` is the JTAG/serial
  bridge, present in ROM and bootloader mode. `27b1:0004` is the OTG CDC ACM,
  present once the Zephyr app runs. Mutually exclusive: the JTAG interface
  disappears as soon as Zephyr starts the OTG stack.
- **`waf --upload`** calls `esptool write-flash 0x0 zephyr.bin` for any board
  whose `ZEPHYR_BOARD` contains `esp32`. Put the board in bootloader mode with
  BOOT plus RESET first, or esptool fails with "Write timeout".
- **Console** appears as
  `/dev/serial/by-id/usb-ArduPilot_esp32s3_zephyr_<MAC>-if00` about a second
  after reset, once the CDC ACM stack initialises.
- **OpenOCD** needs the Espressif fork. The distro 0.12.0 build does not
  support `303a:1001`.

## Regression testing

There is no automated build, flash, soak and compare pipeline, and we are not
building one. The `Tools/scripts/zephyr_*.py` toolkit is the practice: maintain
it, extend it, fix the scripts in place when they break.
[DEBUGGING.md](DEBUGGING.md) lists what each one does.
