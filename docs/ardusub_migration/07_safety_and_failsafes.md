# Safety and failsafes

Current development boundary: `integration/vehicle_defaults.json` sets `actuators.enabled=false`. The ordinary Linux build retains `Empty::RCOutput`; an opt-in Linux test profile substitutes a localhost UDP observer. The serial bridge requires both an explicit flag and an enabled config, while the staged ESP32 sketch has no GPIO/ESC output code. No physical serial port, ESC, flashed firmware or deployed service has been touched. Physical output requires measured wiring and human-supervised commissioning.

The existing reference firmware is not adequate as an unguarded target: `firmware/esp32_thrusters/thruster_esp_final.ino` enables command acceptance 1.5 s after boot, accepts partial indexed commands and uses a 2.5 s timeout that neutralizes but does not revoke the armed state. `esp32_bridge_node.py` can forward 1100–1900 despite nominal mixer limits 1300–1700 and its launch sets a 1.5 s host watchdog. These are source observations, not deployed-firmware confirmation.

The software path now covers atomic eight-channel frames, explicit session challenge, CRC/sequence checks, a 250 ms MCU guard timeout, a 200 ms host observation timeout, neutral startup/restart/shutdown, and latched faults. Native ArduSub mixer output reaches the serial bridge and guarded frame validator in a pseudo-terminal test. Remaining before physical output: measured motor order and polarity; ESP32 Arduino build, flash and fault-injection checks; host crash/USB disconnect behavior on real devices; independent actuator-power isolation and E-stop; and proof of one authoritative low-level owner. Physical actuator power stays disconnected during software validation.
