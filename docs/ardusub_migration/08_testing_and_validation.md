The dashboard now decodes fresh `EKF_STATUS_REPORT` flags into read-only API and CSV fields. A synthetic MAVLink wire test verifies flag parsing and expiry. In the native virtual Xsens/Bar30 dashboard replay, the report remained at flag `1024` (`EKF_UNINITIALIZED`) after about 15 seconds, despite fresh attitude and pressure telemetry. This is direct evidence that the current virtual profile does not establish estimator/navigation readiness; it is not a real-sensor diagnosis. Replayed A50 velocity affecting `XKF1` must not be promoted to `position_ok()` without an absolute position source and a separate navigation check.

The combined virtual Xsens/Bar30 + A50 TCP bridge replay reported EKF flags `167` in one 15-second run: attitude and horizontal velocity were healthy, but `EKF_CONST_POS_MODE` was set and `EKF_POS_HORIZ_ABS` was absent. Repeats reported `1024` (`EKF_UNINITIALIZED`) at 15 and 25 seconds. The replay asserts only that a status report arrives without an absolute-position flag, and logs its value. This exposes inconsistent estimator initialization and the missing navigation-position prerequisite for AUTO/GUIDED; synthetic velocity fusion alone is not readiness.

The phase-aware replay on 2026-11-24 observed startup flags `[0, 167, 1024]`, lock-loss flags `[167]`, and recovery flags `[167, 1024]`, ending at `1024`. This shows the estimator can enter constant-position mode and later become uninitialized in one software run; a final snapshot alone conceals that transition. The Xsens backend currently registers only `IMU` and publishes acceleration/gyro to `AP_InertialSensor`; it stores the Xsens quaternion in ExternalAHRS state but does not publish a compass or separately configured external-navigation yaw source. The DVL replay profile sets `EK3_SRC1_YAW=0` and `EK3_SRC1_POSXY=0`. These source facts and the replay identify missing yaw/position inputs to investigate, not a proven single cause of the transition. Do not change the yaw source to a fabricated value to make a synthetic status pass.
