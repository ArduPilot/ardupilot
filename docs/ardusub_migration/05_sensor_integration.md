# Sensor integration evidence and gates

## Xsens MTi-300

The reference's `xsens_mti_driver_node.py` parses Xbus/MTData2 with quaternion, gyro and accelerometer fields at 100 Hz. The native fork now has `AP_ExternalAHRS_Xsens` (type 12) and a strict MTData2 parser. The parser requires a valid checksum, packet counter, NED quaternion, angular rate and acceleration; it rejects incomplete or duplicate samples. The backend configures those fields at 100 Hz, publishes gyro/accel through `AP_InertialSensor_ExternalAHRS`, and keeps IMU health false without fresh samples. Mount rotation remains an editable identity placeholder; no physical Xsens has been connected.

The parser unit tests and native `./waf sub -j4` build pass. The first virtual-serial run saw no Xbus bytes because the generic Linux board has no barometer: `AP_Baro::init()` entered ArduPilot configuration-error handling before `ins.init()`. A software-only extra hwdef (`integration/atal_linux_test.hwdef`) permits startup without a barometer, and `integration/test_xsens_native_startup.py` then observed GoToConfig, SetOutputConfiguration and GoToMeasurement on a pseudo-terminal. The harness also replays synthetic 100 Hz MTData2 packets and checks that `RAW_IMU` reports the injected acceleration and angular velocity after MAVLink scaling. **Do not use the no-barometer profile for deployment.** Real-sensor timing, calibration, sensor health and EKF initialization remain unverified; a manual replay still reported EKF flags `0`.

## A50 DVL

Manufacturer protocol: [A50 TCP JSON](https://docs.waterlinked.com/dvl/dvl-json-protocol/) at port 16171 and [FRD body axes](https://docs.waterlinked.com/dvl/axes/). The `time` field is milliseconds since last report, `time_of_validity` is Unix microseconds. `velocity_valid` means bottom lock; `velocity_water` is a different measurement. An optional 3x3 covariance is in (m/s)^2, FOM in m/s. The reference driver drops timestamps/covariance and does not handle separate `position_local` reports. New `integration/dvl_velocity.py` rejects invalid reports and transforms velocity with a mount quaternion, body attitude and angular-rate lever-arm correction. It reports an isotropic MAVLink covariance with the same trace because `GCS_Common.cpp:handle_vision_speed_estimate` reduces covariance to sqrt(trace). `integration/dvl_bridge.py` requires a fresh ArduSub attitude/rate sample, suppresses duplicate `time_of_validity`, and sends only velocity estimates to a loopback MAVLink endpoint. It cannot arm or send motor commands. Live A50 access requires `--connect-a50`; no live traffic or estimator fusion has yet been tested. A50 sampling can be 2–15 Hz depending on altitude, so the provisional timeout is 0.75 s.

`integration/test_dvl_mavlink_replay.py` uses a loopback A50 TCP server and simulated ArduSub telemetry to verify the outgoing velocity/covariance MAVLink packet, invalid bottom-lock suppression, duplicate timestamp suppression, stale-attitude suppression and recovery. It does not prove that native ArduSub's estimator fuses the measurement.

Upstream `GCS_Common.cpp` accepts `VISION_SPEED_ESTIMATE` as NED velocity through `AP_VisualOdom_MAV` and `writeExtNavVelData`, provided VisualOdom is configured. `ODOMETRY` also enters the pose pipeline and cannot be populated with fabricated position. Configure `VISO_TYPE` and EKF3 external velocity sources only after native IMU and origin are established. The [ArduPilot non-GPS documentation](https://ardupilot.org/dev/docs/mavlink-nongps-position-estimation.html) describes 4 Hz minimum input and EKF source parameters; actual DVL sampling may fall below that at some altitudes, so mode availability must be tested across real rate limits.

## Bar30

The dedicated reference depth ESP32 reads MS5837 over I²C and publishes `DEPTH:pressure_mbar,temp_c,depth_m` at about 20 Hz and 115200 baud. The new `AP_Baro_ATAL_Depth` backend reads that stream from a separate ArduSub serial port (`SERIALx_PROTOCOL=51`). It converts absolute mbar to Pa, supplies Celsius to `AP_Baro`, and registers a water-pressure sensor. The firmware's surface-relative `depth_m` remains diagnostic; native ArduSub computes depth from absolute pressure and its own surface zero. The parser rejects incomplete, nonfinite, out-of-range and overlong lines. Existing `AP_Baro` freshness checks mark the sensor unhealthy when valid readings stop for 0.5 s. A normal Linux build and virtual Xsens-plus-depth replay passed, including pressure/temperature MAVLink telemetry and loss of the pressure-health bit after malformed depth frames.

`integration/atal_sensor_defaults.parm` keeps the ROS 2 defaults as editable placeholders: Xsens and depth both 115200 baud, with a provisional freshwater specific gravity of 1.0. Assign the actual serial devices and measure the mounting/medium values before vehicle use. Pressure zeroing at the surface, physical calibration, wet operation and estimator initialization remain unverified. The generic Linux board still has no actuator output driver.
