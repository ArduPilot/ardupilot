# Remaining work against the original migration brief

This ledger was reconciled on 2026-11-24 against the original AUV migration instruction, its M1–M9 phases and definition of done, the current code, and the evidence in `08_testing_and_validation.md`. It distinguishes software replay from vehicle qualification. The ROS 2 reference checkout remains the fallback; no change here has been deployed or pushed.

## Software work that can continue without vehicle hardware

1. **Native runtime and reproducibility (M1–M2).** Turn the current development commands and provisional `.parm` files into a reproducible, non-actuating launch/configuration package with explicit serial-device ownership, logging locations, dependency versions, startup order, health reporting, shutdown, and rollback procedure. Verify a clean checkout/submodule build, not only an incremental local build. Keep test-only `ARMING_CHECK=0` and no-barometer profiles out of deployment configuration.
2. **Estimator readiness (M3–M5).** Exercise recorded, realistic Xsens/Bar30/A50 data together over startup, time gaps, bad packets, DVL bottom-lock loss, recovery, and process restarts. Prove EKF initialization and health flags with external velocity selected, not merely `RAW_IMU`, pressure telemetry, or an `XKF1` response to synthetic DVL velocity. A virtual Xsens/Bar30 dashboard replay currently reports `EKF_UNINITIALIZED` after several seconds. Resolve how position/origin and yaw become valid for navigation modes; velocity-only DVL does not establish global position. Add covariance, clock, frame and stale-data checks where the replay exposes gaps.
3. **Allocation behavior (M6).** The provisional policy is to keep upstream ArduSub saturation sharing and linear PWM behavior rather than reproduce the ROS mixer's 35% heave headroom, reverse efficiency, expo and deadband. The source-derived comparison shows up to 0.3 normalized-thrust disagreement in saturated cases. Validate axis authority, response, limits and failures with ArduSub execution in simulation; algebraic rank 6 alone does not prove usable control authority. Revisit the policy after measured thrust curves and dynamics are available.
4. **Actuator software path (M7).** Compile the staged ESP32 sketch with the actual Arduino/ESP32 toolchain. Complete deterministic startup, restart, loss-of-observation, USB disconnect, fault latch/re-arm and emergency-shutdown tests with simulated serial endpoints. The native mixer → observer → guarded serial bridge → parser already passes a pseudo-terminal replay, but the sketch has no GPIO/LEDC/ESC output and the checked-in switch is disabled. Keep that condition until supervised hardware bring-up.
5. **ROS companion ownership (M8).** Preserve useful perception, gate guidance, mission orchestration, diagnostics and logging behind a new companion launch. The current gate launch and dashboard only display proposals; no validated high-level command adapter to ArduSub exists. Define mode/arm/failsafe checks, bounded commands, acknowledgements, stale-proposal handling and cancellation; prove that the old ROS attitude controller, mixer, ESP32 bridge and motor tests cannot run alongside ArduSub as competing owners.
6. **Mission and navigation workflow (M8–M9).** Define waypoint frame/origin, depth reference/sign, yaw, speed, tolerance and hold semantics. Build mission upload/read-back with sequence and ACK checks. Validate `position_ok()`, mode changes, start/pause/abort/skip and disarmed/fault behavior in SITL or equivalent non-actuating replay before enabling dashboard mission controls. See `14_mission_port_boundary.md`.
7. **Dashboard parity (user-requested final integration).** Continue the familiar ROS 2 UI beyond its current read-only shell: mode/parameter/calibration/health panels, mission builder, flight plan, waypoint navigation, throttle/control, Nano/gate, tuning/debug/autotune, camera and logging. Each visible value needs a real ArduSub or companion source, and every command needs an explicit request/ACK/timeout/fault contract. `13_dashboard_field_map.md` records missing fields; `12_dashboard_port.md`, `14_mission_port_boundary.md` and `15_flight_plan_port_boundary.md` define port boundaries. The current API has telemetry, mission status, gate proposals, local CSV and an optional browser camera preview, but no vehicle-command routes or GoPro transport.
8. **Flight-plan evidence and special features.** Port the ROS step sequencer only after each step maps to a supported ArduSub action. Add synchronized video/SRT and milestone reporting after choosing a camera clock source. Untethered launch needs a separately designed trigger, communications and cancel/failsafe path; copying the ROS Ethernet watcher would not establish safety.
9. **System validation (M9).** Run native build/unit/integration tests, ArduSub SITL scenarios, representative ROS bags/sensor logs, fault injection and controller/allocator comparisons as one documented release suite. Record failures and acceptance thresholds. Existing isolated tests and synthetic loopback do not yet establish a full mission or real-time reliability under load.

## Vehicle-dependent final qualification

1. Measure Xsens and A50 mounting rotations/lever arms, Bar30 offset and water density, thruster positions/vectors, motor numbering, ESC polarity, GPIO wiring and the actually deployed ESP32 firmware. Replace the editable ROS-derived placeholders in `integration/vehicle_defaults.json` and matching ArduSub parameters only from measured evidence; rerun layout and replay checks.
2. With propulsion power isolated, validate real Xsens startup/calibration/sample timing, Bar30 surface zero/pressure conversion, A50 frames/rate/bottom-lock behavior, native EKF health, navigation readiness and loss/recovery. Confirm a single process owns each physical sensor.
3. Under human supervision, qualify the real ESP32 serial protocol, flash the reviewed firmware, verify GPIO/LEDC/ESC neutral and ordering, independently inspect actuator-power isolation/E-stop, and inject PC crash, USB disconnect, stale/invalid command and restart faults. Do not energize thrusters merely to run software tests.
4. Only after those gates, commission dry restrained output, then water behavior, control tuning, mission execution, dashboard commands and the tested rollback to the existing ROS 2 deployment. Physical arming, flashing, changing active services and wet tests require separate authorization under the original brief.

## Current verified baseline

- Native Ubuntu x86 ArduSub builds; Xsens and Bar30 virtual-serial replay and A50 synthetic bridge-to-EKF replay pass.
- Eight-channel provisional mapping has rank 6 and a software-only native mixer/guarded serial pseudo-terminal path passes.
- ROS gate companion is proposal-only; dashboard telemetry, mission status and CSV are read-only with an optional HTTP camera preview.
- No actual Xsens, A50, Bar30, ESP32 GPIO/ESC, E-stop, deployed startup service, navigation mission or wet test has passed. The full definition of done in the original brief is therefore **not met**.
